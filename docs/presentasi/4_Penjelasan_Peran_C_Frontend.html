01 · Ikhtisar

Apa yang dikerjakan Peran C?

Peran C membangun lapisan antarmuka pengguna untuk dua kelompok pemakai: peminjam yang menggunakan kiosk tanpa akun, dan petugas IT yang menggunakan panel admin setelah login. Pekerjaan mencakup navigasi halaman, formulir, tampilan data, interaksi, keadaan memuat/kosong/galat, responsivitas, aksesibilitas, serta penghubung frontend ke API yang disediakan backend.

Kiosk

Mengutamakan alur mandiri yang mudah dipahami pada layar sentuh: katalog, transaksi peminjaman, bukti, cek status, klaim pengembalian, perpanjangan, pembatalan pemesanan, dan reset saat idle.

Panel admin

Menyajikan navigasi kerja petugas, tabel dan filter, detail transaksi, verifikasi, pengelolaan master data, pengaturan, akun, audit, serta laporan.

Ringkasnya: frontend menampilkan data dan mengirim aksi pengguna. Validasi akhir, keputusan bisnis, status peminjaman, dan mutasi stok tetap menjadi tanggung jawab backend.

02 · Batas tanggung jawab

Frontend bukan pemilik aturan bisnis

Antarmuka boleh membantu pengguna mengisi data dengan benar dan menyembunyikan atau menonaktifkan aksi yang menurut respons server tidak tersedia. Namun, perilaku UI itu bukan pengganti pemeriksaan server. Backend selalu memvalidasi ulang permintaan dan menentukan apakah suatu aksi sah.

06 · Kiosk

Alur peminjam tanpa akun

Kiosk dirancang sebagai alur layanan mandiri. Peminjam tidak membuat akun; ia memilih barang, mengisi identitas transaksi, lalu menggunakan kode transaksi untuk melihat informasi berikutnya.

Beranda dan katalog

  • Beranda menyediakan jalan pintas ke katalog, peminjaman, dan cek/pengembalian.
  • Katalog memuat barang dari API, menyediakan pencarian nama dengan debounce, filter kategori, dan keadaan memuat, kosong, atau galat.
  • Jumlah tersedia ditampilkan sesuai respons API. Barang dengan stok tersedia nol dapat tampil, tetapi tombol pemilihannya dinonaktifkan.
  • Pencacah jumlah membantu mencegah pilihan pengguna melampaui jumlah tersedia terakhir yang dilihatnya. Server tetap memeriksa ulang saat transaksi dibuat.

Form peminjaman/pemesanan

Form mengumpulkan nama, divisi, tipe peminjam, nomor WhatsApp, keperluan, tanggal pinjam, batas kembali, barang, dan jumlah. Validasi sisi klien memberi umpan balik langsung, tetapi tidak menggantikan validasi backend.

  • Data formulir dan aturan tanggal dibantu fungsi utilitas frontend.
  • Jika tanggal dipilih di masa depan, UI menerangkan bahwa barang dipesan dan stok ditahan menurut aturan server.
  • Satu kunci idempotensi UUID digunakan untuk mencegah pengiriman berulang menjadi transaksi ganda.
  • Tombol kirim dinonaktifkan selama request berlangsung. Jika server merespons konflik stok, UI menampilkan pesan dan memperbarui data yang relevan.
  • Setelah sukses, halaman bukti menampilkan kode dan rincian transaksi; kode tidak dijadikan parameter URL.

Bukti, cek, klaim, dan tindakan lanjutan

  • Bukti peminjaman: kode besar, nama/divisi, keperluan, tanggal, penanda pemesanan jika relevan, batas kembali, daftar barang, dan petunjuk pengembalian. Tata letak cetak menyembunyikan navigasi dan tombol aplikasi.
  • Cek peminjaman: kode dikirim di badan POST, bukan URL. UI menangani kode tidak ditemukan dan pembatasan percobaan tanpa membuka informasi sensitif.
  • Kartu peminjaman: menampilkan status/lencana, informasi batas waktu, ringkasan per barang, sisa dan riwayat klaim, serta alasan kelayakan aksi dari API.
  • Klaim pengembalian: form parsial mencatat jumlah baik/rusak/hilang per barang, membatasi jumlah input sesuai sisa yang dikirim server, menyediakan catatan opsional, konfirmasi, dan kunci idempotensi.
  • Bukti klaim: menunjukkan kode klaim dan status menunggu verifikasi, mengingatkan peminjam untuk menyerahkan barang fisik kepada petugas, serta menyediakan tata letak cetak.
  • Perpanjangan: menampilkan batas lama/baru sebelum konfirmasi dan menyajikan alasan dari server bila tindakan tidak tersedia.
  • Pembatalan pemesanan: merangkum transaksi dan meminta konfirmasi; UI menampilkan hasil backend, bukan mengubah angka stok sendiri.

Reset otomatis saat kiosk ditinggalkan

Composable idle membaca nilai konfigurasi publik kiosk. Setelah tidak aktif, UI menampilkan hitung mundur; interaksi dapat membatalkan hitung mundur. Jika waktu habis, store kiosk dibersihkan dan aplikasi kembali ke beranda. Data peminjam dan kode tidak disimpan di localStorage atau URL.

07 · Panel admin

Antarmuka kerja petugas IT

Login dan sesi

Halaman login mengirim kredensial melalui API sesi. Guard router meminta profil dari /api/auth/me sebelum rute admin terlindungi ditampilkan. Profil admin berada dalam memori Pinia; cookie sesi dikelola browser dan backend. Bila sesi habis, pengguna memperoleh pesan dan diarahkan ke login, dengan tujuan halaman sebelumnya bila tersedia.

Dasbor dan pemantauan

Dasbor merangkum angka dari respons summary backend: peminjaman berjalan, keterlambatan, antrean verifikasi, serta unit stok rusak. Ringkasan diperbarui saat dasbor dimuat dan polling berkala digunakan untuk lencana/menu tanpa me-refresh seluruh halaman.

Barang dan master data

  • Daftar barang memakai pencarian/filter, pagination, form tambah/ubah, dan konfirmasi untuk hapus soft-delete.
  • Penyesuaian stok atau penandaan rusak hanya mengirim aksi beserta alasan ke endpoint; frontend tidak menulis stok.
  • Halaman stok rusak memberi jalur ke penyelesaian perbaikan atau afkir, sesuai hasil dan validasi server.
  • Halaman kategori/divisi menampilkan data, menambah atau mengubah nama, dan mengaktif/nonaktifkan lewat API; konflik seperti kategori masih digunakan disampaikan sebagai galat.

Peminjaman dan verifikasi klaim

  • Daftar peminjaman menggabungkan filter yang disediakan endpoint dan pagination.
  • Detail menampilkan identitas dan barang, lencana, rincian unit, serta lini masa transaksi.
  • Aksi koreksi, perpanjangan, atau pembatalan disajikan melalui form/konfirmasi dan alasan sesuai kebutuhan desain; keberhasilan ditentukan respons server.
  • Antrean verifikasi memisahkan klaim menunggu dari riwayat. Detail verifikasi menyediakan empat hasil per barang: baik, rusak, hilang, atau ditolak.
  • UI memperlihatkan selisih jumlah dan menonaktifkan simpan jika pembagian belum sesuai. Catatan admin wajib ditunjukkan ketika aturan desain mengharuskannya. Server tetap menjadi pemeriksa akhir.

Pengaturan, akun, audit, dan laporan

  • Pengaturan: menampilkan delapan parameter; UI membantu memvalidasi rentang sebelum memperbarui melalui API.
  • Akun admin: daftar/tambah/nonaktifkan akun dan ganti kata sandi sendiri; UI mencegah tindakan yang tidak sesuai, sementara backend memvalidasi.
  • Jejak audit: tabel hanya baca dengan filter dan tampilan rincian peristiwa.
  • Laporan: pilihan jenis, filter tanggal/kategori yang relevan, unduhan PDF dengan nama berkas dari header respons, dan penanganan galat JSON bila unduhan gagal.
  • Halaman galat: pesan ramah untuk 403, 404, dan 419 serta rute catch-all, tanpa menampilkan rincian internal server.

08 · Integrasi API dan state

Kontrak request/response di sisi UI

Frontend mengelompokkan pemanggilan endpoint ke dalam klien kiosk, autentikasi, dan admin. Komponen memanggil fungsi klien tersebut sehingga URL endpoint, metode HTTP, dan pengaturan response tidak tersebar di setiap halaman.

Kelompok klienContoh interaksi UIPola
KioskConfig, katalog, kategori, divisi, buat transaksi, lookup kode, klaim, perpanjangan, batal.Endpoint publik; kode dikirim di request body untuk operasi lookup/aksi.
AuthLogin, profil sesi, logout, ganti kata sandi.Cookie sesi Sanctum dan CSRF; request dengan kredensial ke origin aplikasi.
AdminSummary, barang, peminjaman, klaim, master data, pengaturan, audit, laporan.Rute terlindungi sesi; parameter filter dikirim sebagai query sesuai kontrak.

Penanganan respons dan galat

  • Jaringan tidak tersedia: pesan koneksi umum dan kesempatan mencoba kembali.
  • 401: rute admin mengarahkan ke login; pesan sesi berakhir dibedakan dari keadaan belum pernah login.
  • 419: CSRF dicoba diperbarui dan request diulang sekali; kegagalan sesudahnya ditampilkan dengan pesan yang sesuai, tidak dianggap otomatis sebagai sesi habis.
  • 403: akses ditolak dengan pesan yang aman.
  • 409: konflik bisnis/stok ditampilkan agar pengguna dapat meninjau ulang data.
  • 422: detail kesalahan field dipetakan ke formulir terkait dan ringkasan galat disajikan.
  • 429: UI menggunakan informasi jeda Retry-After bila tersedia.
  • 500 atau galat jaringan: pesan umum tanpa jejak internal backend.

Pengelolaan state

  • State navigasi umum disimpan dalam router.
  • Data kiosk yang berkaitan dengan form/kode berada dalam store Pinia runtime dan dibersihkan saat idle/reset.
  • Profil admin dan ringkasan berada dalam store sesi; bukan tempat menyimpan password atau kode peminjaman.
  • Notifikasi dan state layout dipisah ke store/composable yang sesuai.

09 · Mutu UI

Keamanan, privasi, aksesibilitas, dan responsivitas

Kode transaksi tidak bocor ke URL

Kode pinjam/klaim ditransmisikan melalui body request dan state memori, bukan query path atau localStorage.

Minimisasi data kiosk

Frontend kiosk menampilkan kontrak publik dan tidak menyimpan nomor kontak peminjam sebagai data persisten.

Validasi aman

Konten dari server ditampilkan sebagai teks biasa; tidak memakai mekanisme HTML mentah untuk data pengguna.

Sesi admin

Autentikasi memakai cookie sesi/CSRF, bukan menyimpan token autentikasi di localStorage.

Aksesibilitas

Label input, fokus yang terlihat, status/galat yang dapat diumumkan, tombol dengan nama yang bermakna, dan indikator tekstual selain warna.

Layar beragam

Kiosk ditata untuk sentuh; panel admin menggunakan menu geser dan mode kartu tabel pada viewport sempit.

Target UI yang tercatat mencakup layar 360 px dan 768 px, target sentuh kiosk minimal 44 × 44 px, state memuat/kosong/galat, cetak tanpa navigasi, dan pesan ramah untuk kondisi sesi/akses.

10 · Verifikasi

Bagaimana bagian frontend diuji?

Catatan task C menyebut pengujian kompilasi komponen, tes unit/utilitas, tes halaman, build produksi, serta skenario manual untuk alur kiosk dan panel admin. Validasi API/backend tetap memiliki suite terpisah pada bagian A/B.

Jenis pemeriksaanContoh yang diperiksa
Buildnpm run build memastikan aplikasi dapat dikompilasi untuk produksi.
Tes frontendnpm test menjalankan tes komponen, fondasi admin, halaman, kiosk, dan utilitas tanggal yang tercantum pada script saat ini.
Uji alur kioskPeminjaman, pengiriman berulang, kode tidak di URL/riwayat, cetak, responsivitas, validasi, serta idle reset.
Uji alur adminGuard sesi, status badge konsisten, tabel responsif, halaman galat, dan perilaku halaman pengelolaan.
Verifikasi kontrakFrontend diuji bersama respons API yang tersedia; bentuk API harus mengikuti kontrak backend, bukan ditebak dari placeholder.
Hasil tes yang tertulis di log task adalah bukti pada saat task tersebut diverifikasi. Sebelum demo atau rilis, jalankan kembali perintah tes pada branch/build yang benar dan gunakan hasil terbaru.

Contoh penjelasan lisan tentang bagian C

Hal yang sebaiknya tidak diklaim

  • Jangan menyebut frontend mengubah stok atau menghitung status peminjaman.
  • Jangan mengklaim seluruh proyek siap produksi hanya karena task UI telah dicentang.
  • Jangan menyebut jumlah tes terkini kecuali sudah menjalankan ulang suite yang relevan dan memeriksa hasilnya.
  • Jangan mengatribusikan Service, Controller, endpoint, migrasi, atau aturan domain sebagai implementasi C.
  • Jangan menyebut Task 1.19b sebagai pekerjaan C saja; itu kerja bersama A, B, dan C.
